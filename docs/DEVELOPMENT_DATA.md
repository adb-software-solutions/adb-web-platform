# Development data

The ADB Business Platform includes deterministic fake data tooling so the admin application can be developed and reviewed against realistic volumes rather than empty tables.

## Recommended management command

After migrations have been applied, generate the complete development data set from `backend/`:

```bash
python manage.py seed_all_development --reset
```

This is the command to use for normal local platform development. It populates the core operational/CMS data and the extended infrastructure inventory in one run.

Increase the volume when testing denser tables, search or pagination:

```bash
python manage.py seed_all_development --reset --scale 3
```

The underlying seeders refuse to run when `DEBUG=False`. A `--force` escape hatch exists only for disposable non-production environments and should not be used against real platform data.

`--reset` removes records created by the development seeders before rebuilding the demo set. It does not flush the whole database and does not intentionally remove normal development records.

The lower-level `seed_development` and `seed_infrastructure_development` commands remain available when working on a specific subset, but `seed_all_development` is the canonical local-development entry point.

## Data created

At scale 1 the full command currently creates approximately:

- 3 ADB Brands;
- 18 fake clients with multiple contacts;
- 28 projects and project notes;
- 140 time entries;
- 45 CRM leads and pipeline reference records;
- 90 client/project tasks plus standalone internal operational tasks, statuses and lists;
- 36 knowledge-base documents with version history;
- 20 fake credential records;
- servers, PostgreSQL instances, websites, domains, licences and logical applications;
- website technology-stack records;
- SSL certificates with varied development expiry dates;
- mobile applications;
- REST/GraphQL API inventory records;
- automation bots;
- Microsoft 365-style email-system inventory;
- brand-aware blog posts, categories, tags, FAQs, testimonials and case studies;
- audit events for recent-activity interfaces.

Credential values generated by the command are explicit placeholders such as `demo-password-not-a-real-secret`. The existing credential model is not approved for production secrets until encrypted-at-rest storage is implemented.

## Local test workflow

For a fresh or newly migrated development environment:

```bash
cd backend
python manage.py migrate
python manage.py seed_all_development --reset
```

If you want a much denser dataset:

```bash
python manage.py seed_all_development --reset --scale 3
```

Use a local superuser when reviewing the whole platform. Normal staff users intentionally see only the capabilities and client scopes granted to them, so a restricted staff account may correctly display only part of the seeded dataset.

If you do not already have a local superuser:

```bash
python manage.py createsuperuser
```

Then start the backend and admin applications using the normal devcontainer tasks/scripts and sign into the admin through the authentication application.

## Reference fixture

`apps/core/fixtures/development_reference.json` contains a small baseline fixture for reference/taxonomy data such as lead sources, task statuses, credential types and knowledge-base sections.

It can be loaded into a clean development database with:

```bash
python manage.py loaddata apps/core/fixtures/development_reference.json
```

The comprehensive development seed commands do not require this fixture; they create or update the reference values they need themselves. Prefer `seed_all_development` for normal platform development.

## Rules for development data

- Never copy real client credentials, contact details or private infrastructure data into fixtures.
- Use reserved documentation/example domains and clearly fake people/companies.
- Keep seed generation deterministic unless randomness itself is the feature under test.
- When a new operational model is added, consider whether realistic seeded records are useful for its admin UX.
- Seed data is for development and demos, not test assertions that require exact production-like IDs.
